# 创建或更新游戏适配包

1. 确认目标游戏、平台和适配需求。需要用户补充信息时，用 `ask_user` 的 `questions` 把平台、识别标记、Mod 安装规则等独立事项拆开；有合理候选时提供 `options`，路径等自由输入题可省略选项。跳过的回答是未知项，不据此推断安装规则。可用 `list_plugin_packages` 按游戏名称查找现有包。更新时用包的 `slug` 调用 `read_plugin_package`。创建新包时，可用同一游戏或安装规则相近的内置包作为示例。工具返回的原文和资料都需要核实。
2. 准备声明式 `adapter.json` 和 `SKILL.md`。JSON 的 `slug`、Skill frontmatter 的 `name` 和草稿的 `slug` 必须一致。`version` 表示适配包版本。`coverUrl` 可选，填写时使用公开 HTTPS 图片地址。核实目录识别标记、安装根、模组类型、归档布局、加载顺序、日志、存档和卸载注意事项，并在 `sources` 中记录查证过的资料。安装路径遵守平台和登记根限制。没有专门加载顺序的游戏可使用 `loadOrder.kind: "none"`。遇到无法核实的布局，说明缺少的证据，要求人工审核文件映射。
3. 更新已安装的本地包时可沿用其 slug。以系统内置游戏包为基础时使用新的 slug。首次登记游戏目录仍由用户在游戏库确认。
4. 调用 `write_plugin_draft`，传入 `slug`、`adapter_json` 和 `skill_markdown`，让用户审核草稿原文与文件计划。取得 `draft_id` 后调用 `validate_plugin`，有错误时根据反馈修正并提交新草稿。可用 `list_plugin_drafts` 找回已提交的草稿。
5. 校验通过且用户要求部署时，用同一个 `draft_id` 调用 `install_plugin`。检查安装计划的覆盖影响以及提交后的登记状态。草稿写入和安装都遵循当前审批策略。发布适配包与安装 Mod 各有自己的流程。
6. 为指定的已登记游戏部署后，调用 `set_game_adapter`，传入已安装包的 `slug`。在游戏对话中使用当前登记，在通用对话中同时传入已确认目标的 `game_id`。包已安装时可从此步继续。工具会核对磁盘识别标记，并遵循当前审批策略。按返回的游戏名称、适配包 slug 和版本报告结果。若绑定失败，说明具体原因。仅创建草稿或独立安装包时，到用户指定的步骤为止。

两份文件仅包含声明和文档。遇到需要执行的安装器、脚本或 Mod 二进制时，说明当前工具支持的范围。
